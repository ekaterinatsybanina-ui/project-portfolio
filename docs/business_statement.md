# Бизнес-постановка: «Единая панель портфеля проектов университетского отдела»

> **Как читать документ.** Про отдел известно только то, что он реализует проекты в сфере образования, науки и технологического предпринимательства. Всё остальное (процессы, инструменты, цифры) помечено как **[Гипотеза]**: это типичная ситуация для такого отдела, её нужно подтвердить интервью с руководителем отдела. **[Факт]** означает сведения от автора проекта. Все данные в приложении **синтетические**, это не данные реального университета.

## 1. Название проекта
«Портфель-панель»: приложение для мониторинга проектного портфеля отдела образования, науки и технологического предпринимательства.

## 2. Описание компании и её деятельности
- **[Факт]** Университетский отдел реализует проекты в трёх направлениях: образование, наука, технологическое предпринимательство.
- **[Гипотеза]** Одновременно ведётся 15–40 проектов: образовательные программы и интенсивы, научные гранты и НИОКР, акселераторы и стартап-студии, конкурсы и хакатоны.
- **[Факт]** В команде 10 человек. Роли — от специалиста по проектной деятельности до ведущего специалиста (по данным автора проекта; точное число людей на каждом уровне неизвестно).
- **[Гипотеза]** Сотрудники совмещают работу сразу в нескольких проектах, поэтому нагрузку удобно считать по всем проектам сразу.
- **[Гипотеза]** Внешние стороны: партнёры-компании, грантодатели, студенты и исследователи, ректорат или проректор, которому отдел отчитывается.

## 3. Текущий процесс AS-IS **[Гипотеза]**
1. Менеджер ведёт свой проект в личной таблице или документе.
2. Раз в неделю или месяц руководитель просит прислать статус по проектам.
3. Менеджеры присылают статусы в мессенджер или на почту в разном формате.
4. Помощник или руководитель вручную сводит данные в общую таблицу и презентацию для вышестоящего руководства.
5. Нагрузка сотрудников оценивается «на глаз»; риски обсуждаются на планёрках.
6. Проблемы (срыв сроков, перерасход, перегрузка человека) выявляются поздно.

## 4. Проблема и узкое место
**Нет единой, актуальной и сопоставимой картины по портфелю.** Узкое место находится на шаге 4: ручной сбор и свод статусов. Он занимает время, содержит ошибки и всегда отстаёт от реальности.

## 5. Причины **[Гипотеза]**
- Данные хранятся в разных файлах и чатах без единого формата.
- Нет общих правил: что считать риском, как часто обновлять статус.
- Нет автоматического сопоставления плана и факта: время, бюджет, прогресс.
- Нагрузка на сотрудников не считается по всем проектам сразу.
- Универсальные системы управления проектами слишком тяжёлые для небольшого отдела либо платные.

## 6. Заинтересованные стороны и пользователи
| Роль | Интерес | Как использует |
|---|---|---|
| Ведущий специалист / руководитель отдела | Видеть риски раньше, быстро готовить отчёт | Дашборд, еженедельный отчёт, нагрузка команды |
| Специалист по проектной деятельности | Не тратить время на отчёты | Быстрое обновление статуса своих проектов |
| Координатор / помощник | Исключить ручной свод | Выгрузка отчёта в Excel и Markdown |
| Проректор / руководство вуза | Прозрачность портфеля | Получает готовый отчёт (косвенный пользователь) |

## 7. Бизнес-цель
Сократить время подготовки отчёта по портфелю и выявлять проекты, сотрудников и сроки с риском до того, как проблема станет срывом. Целевые значения задаёт отдел; в учебном проекте они приведены как гипотезы (раздел 14).

## 8. Задачи проекта
1. Описать единую модель данных проекта: направление, сроки, бюджет, прогресс, контрольные точки.
2. Реализовать автоматический расчёт риска проекта по прозрачным правилам.
3. Реализовать расчёт загрузки сотрудников по всем активным проектам.
4. Реализовать дашборд и формирование еженедельного отчёта в один клик.
5. Реализовать оценку экономического эффекта по параметрам, которые вводит пользователь.
6. Покрыть тестами расчётную логику и опубликовать код на GitHub.

## 9. Процесс TO-BE
1. Менеджеры обновляют по своим проектам три поля: прогресс, фактические расходы, статус. Это занимает 1–2 минуты на проект.
2. Приложение само считает плановый прогресс по датам, отставание, перерасход, просроченные контрольные точки, «устаревшие» статусы.
3. Руководитель открывает дашборд и сразу видит красные и жёлтые проекты с причинами.
4. Вкладка «Нагрузка» показывает перегруженных и недогруженных сотрудников.
5. Еженедельный отчёт формируется кнопкой и скачивается в Excel или Markdown.

## 10. Концепция приложения
Локальное веб-приложение на **Streamlit** с базой **SQLite**. Запускается одной командой на обычном компьютере, без платных сервисов и API. Бизнес-логика вынесена в отдельный модуль, поэтому её можно тестировать без интерфейса и заменить интерфейс при необходимости.

## 11. Функциональные требования
| № | Требование |
|---|---|
| ФТ-1 | Хранить проекты: название, направление, руководитель, статус, даты, плановый и фактический бюджет, фактический прогресс, дата последнего обновления |
| ФТ-2 | Хранить контрольные точки проекта с датой и признаком выполнения |
| ФТ-3 | Хранить сотрудников и их назначения на проекты (часов в неделю) |
| ФТ-4 | Рассчитывать плановый прогресс по датам и отставание от него |
| ФТ-5 | Рассчитывать риск проекта (0–100) и уровень: зелёный, жёлтый, красный, с перечнем причин |
| ФТ-6 | Рассчитывать загрузку сотрудников и помечать перегруженных и недогруженных |
| ФТ-7 | Показывать дашборд: KPI портфеля, разрез по направлениям, список проблемных проектов |
| ФТ-8 | Добавлять проект и обновлять статус проекта через форму с проверкой ввода |
| ФТ-9 | Отмечать контрольные точки выполненными |
| ФТ-10 | Формировать отчёт и скачивать его в Excel и Markdown |
| ФТ-11 | Оценивать эффект от автоматизации по параметрам, введённым пользователем |
| ФТ-12 | Загружать и пересоздавать синтетические демо-данные |

## 12. Нефункциональные требования
- Python 3.10+, запуск на Windows, macOS, Linux.
- Только бесплатные библиотеки: streamlit, pandas, openpyxl, pytest.
- Данные локально в SQLite, без передачи в сеть.
- Расчёт на 100 проектов происходит быстрее секунды.
- Понятные сообщения об ошибках ввода.
- Код разделён на слои (интерфейс / логика / база), читаем и защищаем на уровне студента.

## 13. Границы MVP
**Входит:** ФТ-1…ФТ-12, одна роль пользователя, демо-данные.
**Не входит:** авторизация и роли, интеграции с почтой, Jira или календарями, уведомления, ИИ-прогнозы, история изменений, мультипользовательская работа.

## 14. KPI и расчёт
| KPI | Формула | Статус |
|---|---|---|
| Доля проектов с актуальным статусом | проекты в работе, обновлённые за последние 14 дней / все проекты в работе | считается приложением |
| Доля проектов в красной зоне | красные / проекты в работе | считается приложением |
| Просроченные контрольные точки | число невыполненных точек с датой раньше сегодняшней | считается приложением |
| Перегруженные сотрудники | сотрудники с загрузкой выше 100% | считается приложением |
| Исполнение бюджета | фактические расходы / плановый бюджет активных проектов | считается приложением |
| Время подготовки отчёта | часы «до» и «после» | **вводит пользователь**; значения по умолчанию в приложении гипотетические |

## 15. Ожидаемый бизнес-эффект **[Гипотеза]**
- Сокращение трудозатрат на свод отчётности (оценка зависит от числа проектов и частоты отчётов; считается во вкладке «Эффект» на введённых данных).
- Более раннее выявление рисков: просрочка и перерасход видны в день появления, а не на планёрке.
- Выравнивание нагрузки, меньше выгорания ключевых сотрудников.
- Единый формат данных для отчётов вышестоящему руководству.

## 16. Ограничения, риски, допущения
**Допущения:** менеджеры согласны вносить статус; процессы отдела похожи на описанные в AS-IS.
**Ограничения:** правила расчёта риска упрощены и настраиваются в коде; прогресс вносится вручную; один пользователь.
**Риски:**
| Риск | Мера |
|---|---|
| Менеджеры не обновляют данные | Метка «статус устарел» делает проблему видимой |
| Правила риска не подходят отделу | Пороги вынесены в константы и описаны в README |
| Данные в демо принимают за реальные | Явная пометка «синтетические данные» в интерфейсе и README |

## 17. Критерии приёмки
1. Приложение запускается по инструкции из README без ошибок.
2. На демо-данных на дашборде виден хотя бы один проект каждого уровня риска.
3. Некорректный ввод (даты, отрицательный бюджет, прогресс вне 0–100) отклоняется с понятным сообщением.
4. Для проекта в красной зоне показаны причины.
5. Отчёт скачивается в Excel и Markdown и содержит KPI и список проблемных проектов.
6. Все автотесты проходят командой `pytest`.
7. Код опубликован в репозитории GitHub с README.
